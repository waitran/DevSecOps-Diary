## ⚙️ 1. Управление процессами в Linux
Каждая запущенная программа — это процесс. У него есть PID (Process ID), владелец и состояние.

```bash
# Посмотреть все запущенные процессы (полный список)
ps aux

# Найти конкретный процесс по имени (например, nginx)
ps aux | grep nginx

# Интерактивный мониторинг ресурсов (аналог Диспетчера задач)
top
# или более современный и красивый вариант:
htop

# Завершить процесс по PID (вежливый запрос на завершение, SIGTERM)
kill <PID>

# Принудительно убить процесс, если он не отвечает (SIGKILL)
kill -9 <PID>

# Управление службами (демонами) через systemd
sudo systemctl status ssh      # Проверить статус службы
sudo systemctl restart nginx   # Перезапустить службу
sudo systemctl enable ufw      # Добавить службу в автозагрузку
```

## 🌊 2. Перенаправление потоков (I/O Redirection)
В Linux у каждой программы есть 3 стандартных потока. Умение ими управлять — основа написания Bash-скриптов и парсинга логов.

| Поток | Описание | Номер (FD) |
| :---: | :--- | :---: |
| **stdin** | Стандартный ввод (клавиатура) | `0` |
| **stdout** | Стандартный вывод (успешный результат на экран) | `1` |
| **stderr** | Стандартный поток ошибок (сообщения об ошибках) | `2` |

### Операторы перенаправления:
```bash
# >  : Перезаписать файл выводом команды (старое содержимое удалится)
echo "Hello" > output.txt

# >> : Дописать вывод команды в конец файла (безопасно для логов)
echo "Log entry" >> output.txt

# |  : Pipe (конвейер). Передать вывод одной команды на вход другой
ps aux | grep python

# 2> : Перенаправить только ошибки в файл
ls /nonexistent_dir 2> errors.log

# 2>&1 : Перенаправить ошибки (2) туда же, куда идет стандартный вывод (1)
# Полезно, чтобы сохранить и успех, и ошибки в один лог-файл:
./script.sh > all_logs.log 2>&1

# /dev/null : "Черная дыра". Тихое удаление ненужного вывода или ошибок
curl -s https://example.com > /dev/null 2>&1
```

## 🌐 3. Сетевые утилиты (Диагностика)
`curl` — основной инструмент для проверки доступности сервисов, API и анализа заголовков.

```bash
# 📥 GET-запрос: получить тело ответа
curl https://github.com

# 📋 HEAD-запрос: получить только заголовки (быстрая проверка статуса)
curl -I https://github.com

# 🔍 Verbose: показать весь процесс, включая DNS, TCP и TLS handshake
curl -v https://github.com

# 📤 POST-запрос: указать метод и отправить данные
curl -X POST -d "username=admin&password=123" https://api.example.com/login

# 🔐 Авторизация: добавить кастомный заголовок (Header)
curl -H "Authorization: Bearer YOUR_TOKEN" https://api.example.com/data
```

### Проверка открытых портов (`ss`)
> 💡 **Pro Tip:** В современных Linux вместо устаревшего `netstat` используется `ss` (socket statistics). Она работает быстрее и читает данные напрямую из ядра.

```bash
# Базовая проверка слушающих портов
sudo ss -tuln

# Расширенная проверка с именами процессов (Рекомендуется!)
sudo ss -tulnp
```
**Расшифровка флагов `ss`:**  
`-t` (TCP), `-u` (UDP), `-l` (Listening/слушающие), `-n` (Numeric/числа вместо имен сервисов), `-p` (Process/имя процесса и PID).

## 🛡️ 4. Фаерволы: UFW и Iptables
UFW (Uncomplicated Firewall) — это удобный фронтенд для управления низкоуровневым `iptables`/`nftables`.

> [!WARNING] 
> **ЗОЛОТОЕ ПРАВИЛО:** Всегда добавляй правило для разрешения SSH (`allow 22/tcp`) **ДО** включения фаервола (`ufw enable`), иначе ты заблокируешь сам себя!

### Базовое управление UFW:
```bash
sudo ufw status          # Проверить текущий статус и правила
sudo ufw enable          # Включить фаервол
sudo ufw disable         # Временно отключить
sudo ufw reset           # Сбросить все правила к заводским настройкам
```

### Настройка правил доступа:
```bash
# ✅ Разрешить базовые сервисы
sudo ufw allow 22/tcp            # Разрешить входящий SSH
sudo ufw allow 80,443/tcp        # Разрешить веб-трафик (HTTP/HTTPS)

# ❌ Явный запрет
sudo ufw deny 3306               # Запретить внешний доступ к MySQL

# 🎯 Точечный доступ (Best Practice)
sudo ufw allow from 192.168.1.0/24 to any port 22  # SSH только из доверенной подсети

# 🗑️ Управление правилами
sudo ufw status numbered         # Показать правила с номерами
sudo ufw delete 3                # Удалить правило под номером 3
```

### Iptables (Низкоуровневое управление):
```bash
# Показать все текущие правила с номерами строк
sudo iptables -L -n -v --line-numbers

# Добавить правило: разрешить входящий TCP-трафик на порт 22
sudo iptables -A INPUT -p tcp --dport 22 -j ACCEPT

# Удалить правило: удалить 1-е правило из цепи INPUT
sudo iptables -D INPUT 1
```

## 📜 5. Логирование и мониторинг атак (SOC Focus)
Включи логирование заблокированных пакетов, чтобы анализировать попытки сканирования или атаки.

```bash
# Включить логирование (уровни: off, low, medium, high, full)
sudo ufw logging medium

# Просмотр заблокированных попыток в реальном времени (Ubuntu 20.04+)
sudo journalctl -u ufw -f
```

## ☠️ 6. Базовые сетевые атаки (
Понимание механики атак необходимо для их выявления в логах и трафике.

| Атака | Уровень OSI | Механика | Как обнаружить (IOC) |
| :--- | :---: | :--- | :--- |
| **ARP Spoofing** | 2 (Канальный) | Злоумышленник отправляет поддельные ARP-сообщения, связывая свой MAC-адрес с IP-адресом легитимного шлюза. Трафик жертвы идет через атакующего (Man-in-the-Middle). | Аномальное изменение MAC-адреса шлюза в ARP-таблице (`arp -a`), дублирование IP в сети. |
| **DDoS (L3/L4)** | 3-4 (Сетевой/Транспортный) | Переполнение канала связи или ресурсов сервера огромным объемом мусорного трафика (например, SYN-flood, UDP-flood). | Резкий скачок входящего трафика, рост числа полуоткрытых TCP-соединений, загрузка CPU сетевым стеком. |
| **Brute-Force** | 7 (Прикладной) | Множественные автоматизированные попытки подбора пароля (SSH, RDP, веб-формы). | Множество событий "Failed password" или "401 Unauthorized" с одного или распределенных IP за короткое время. |

## 🧠 DevSecOps Mindset
1. **Принцип наименьших привилегий (PoLP):** Никогда не оставляй порты открытыми "на всякий случай". Если порт не нужен снаружи — `deny` или ограничь его конкретной подсетью.
2. **Анализ логов:** Регулярный просмотр `ufw.log` или `auth.log` позволяет выявить попытки брутфорса или сканирования портов на ранних стадиях.
3. **Shift-Left в инфраструктуре:** Правила фаервола должны быть описаны кодом (IaC, например, в Ansible или Terraform), а не настроены вручную через CLI, чтобы избежать дрейфа конфигураций.
